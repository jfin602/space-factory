SCOPE AND STEPS
1. Extend the existing processor panel with explicit Start and Stop intents that set its enabled state. A single state-labeled button or separate actions is sufficient, but the command carries the desired state rather than blindly toggling. Repeated Start/Stop requests are idempotent: they cannot reset progress, refund/debit input again, create another job, or cause an unintended opposite transition. Starting enables eligible work; unmet requirements produce the actual waiting/blocked reason. Stopping retains the existing job, progress, and material.
2. Route these commands through the existing single action dispatcher. Require the matching active panel opening, Walking mode, processor target identity, and current range when applying an action. A callback from a closed/replaced opening remains invalid even after reopening the same target. Keep transactions synchronous and preserve P2's E/Escape close, out-of-range invalidation, movement while a panel is open, handled-input rules, and Piloting E exit. Do not create another mode owner or per-machine E listener.
3. Present enabled intent separately from actual operating status. Show Off, Running, Missing input, or Blocked output according to the shared job contract, plus the installed starter solar condition. If the actual power requirement is unsatisfied, expose its real cause. An active paid-for job is not missing input merely because its input buffer is now empty. Off/blocked jobs retain readable progress; completed blocked work must not appear to have started another cycle.
4. Show current input ice, processor output, tank quantity/capacity, cycle progress, and relevant connection state. Read existing authoritative owners, not label-owned counters. Keep compact factory status/tank information available while Piloting so continuing production can be inspected without reopening a Walking-only panel. Preserve readable action success/failure feedback through HUD refresh, and prevent new displays from hiding the engineer, machinery, or helm.
5. Reuse compatible pixel-art wiring from P2 and the starter pack. Drive processor_idle.png / processor_active.png from actual processing activity; an enabled but starved, stopped, or blocked processor must not falsely appear productive. Existing solar, tank, pipe, and resource-icon assets are sufficient. Preserve nearest filtering, registered frame sizes, native/integer positioning where applicable, ship-local ownership, and independent interaction/collision bounds. Do not regenerate art or introduce an animation framework.
6. Drive flow feedback only from actual positive transfer events/quantities. A brief retained pulse may make a real event readable, but an installed pipe or nonempty tank alone must not animate ongoing flow. Stop can leave existing output draining into the tank, and presentation must reflect that distinction. UI refresh and visual pulse timing must never advance the resource simulation or call delivery a second time.
7. Make helm feedback truthful as fuel becomes available. With an empty tank, explain the empty reserve. With stored propellant, do not claim that propellant is missing; explain that applied propulsion is not available in this phase. Keep normal ship motion and thrust/exhaust disabled until M1-P4. The spatial fixture remains explicitly labeled development translation.
8. Add focused checks through actual panel commands and state adapters. Cover repeated Start/Stop, retained job/progress, stale/wrong-target/out-of-range/Piloting rejection, feedback after refresh, state-to-progress/activity/flow mapping, and zero-versus-nonzero-tank propulsion messages. Verify that closing panels and entering/leaving Piloting neither pause production nor recreate jobs or resources. Adapt old unconditional P2 zero-output/tank assertions only to fresh/off-state boundaries; preserve their accounting, capacity, control, and spatial protections.
